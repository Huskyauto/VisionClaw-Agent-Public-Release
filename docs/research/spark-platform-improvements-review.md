# Spark Top-3 improvements — engineering assessment

Source: owner-supplied `Top-3_Improvements_Spec_v1_1792573629384.0 (Markdown)`,
version 1.0 dated 2026-10-21. Assessment only; no implementation, paid evaluation,
production change, or publication was performed for this review.

## Verdict

Useful platform roadmap, but not a direct remedy for the observed company-package
failures. Retain the phased approach; revise the fact-checking and evaluation
requirements before implementation. Do not insert additional juries into the
currently approved company-package workflow by inference from this document.

## Comparison with observed failures and code

- The failed fresh company package used retained model output after three authors
  completed. Its rejected fact block combined nonadjacent lines from a single
  retained source. This was an acceptance/representation mismatch, not a wrong
  tool choice or a demonstrated false numeric claim.
- `server/lib/company-compilation-matrix.ts` uses nine author operations and three
  syntheses, with durable claims and retained responses. It explicitly does not
  invoke juries or purchase automatic retries.
- `server/lib/company-compilation-content.ts` supplies the model contract and
  normalizes supported formatting before the shared evidence validator runs.
- `server/lib/business-report-evidence.ts` separates facts, recommendations and
  assumptions. Proposed economics need formulas and verification, not fabricated
  historical primary-source proof.
- `server/tool-registry.ts` has category/speed/network/product metadata, not the
  six-field documentation contract proposed in WI-1. This is a real extension,
  not proof that existing descriptions are all deficient.

## WI-1 — tool documentation

Proceed as a bounded, measured pilot, not a mass rewrite. Keep compact purpose
and wrong-use guidance at the start of model-visible descriptions; long repeated
metadata costs tokens and can be truncated by discovery/routing surfaces.
Documentation of cost, side effects and tenant scope must not become an
authorization source or replace executable policy.

Freeze tasks, model configuration and scoring before rewriting descriptions.
Use paired repetitions and report uncertainty; one response per task cannot
establish that a stochastic model never regresses.

## WI-2 — outcome ownership

Useful for reducing manual relays, not an immediate report-validator repair.
First test outcome-shaped instructions against the existing mission machinery;
add schema/schedulers only if measured behavior requires them. Proactive source
access needs server-side enforcement, item identity, deduplication, deadlines,
bounded spend and a stop switch. Observations/proposals must not be confused
with approval or executed-action receipts in the ledger.

## WI-3 — adversarial review

Trial only as an explicitly approved, separately budgeted mode. Additional
review calls do not remove deterministic contract mismatches and may increase
latency, cost and false positives. Independent sessions can share correlated
model errors; require evidence, not just different seat names.

Replace the blanket primary-source rule for every number with claim classes:

1. Observed external facts: retained source plus locator.
2. Computed results: source inputs plus reproducible calculation.
3. Planning assumptions/targets: clear labels, formulas where relevant and
   validation steps; never presented as achieved facts.
4. Owner-set offer prices, budgets and schedules: authorized configuration or
   instructions, not invented external-source requirements.

Material unsupported factual claims can block delivery; legitimate assumptions,
recommendation timelines and owner prices must not fail merely for lacking
historical external evidence. Define actionable judge escalation precisely.
Do not silently reduce reviewer coverage and retain the same assurance label.

## Immediate preventive priority

Maintain one versioned model/validator contract, a no-provider retained-response
replay corpus spanning authors/categories, clear separation of harmless formatting
from substantive failure, and useful failure diagnostics. Preserve paid receipts
and completed work. Offline replay is not proof that unfinished live production
steps have completed.

## Follow-up: completed catering package versus failed dental package

Production read-only inspection confirmed the catering package completed, while
the new dental package blocked on its first author. Exact offline replay found
two independent checks, not a general provider outage:

- Genuine audit excerpts were reordered within a fact block. Recovery can split
  these into separately labeled excerpts, each matched against the SAME declared
  source. There is no need to impose original source order on independent
  excerpts. This does not permit paraphrases, cross-source borrowing, invented
  facts, or excess section blocks.
- The original author JSON was 26,102 canonical characters, already above the
  existing 25,000-character input allowance. Fixing excerpt representation does
  not fix this independent size violation. The limit remains enforced; no prose
  was dropped and no new provider call was made.

All twelve retained responses from the completed catering package pass the
updated offline acceptance checks. The dental response still correctly stops at
the size bound. A package being blocked is distinct from its worker invocation
successfully persisting that blocked outcome.

### Priority among the three ideas

WI-2 outcome ownership is now the clearest priority, but it needs actual routing
and continuation, not just mission fields. The package catch records/logs a
blocked outcome and returns; it does not itself dispatch a report repair.
Do not mistake that for a functioning closed-loop recovery path. WI-1 can
improve agent tool selection later. WI-3 is suitable for independent adversarial
regression checks, not an extra paid jury around every generated report.

### Proposed bounded recovery contract — NOT implemented or authorized

1. Persist a classified, tenant/operation/receipt-bound failure.
2. Apply only deterministic, source-proven representation repairs to saved data;
   run the unchanged validator and leave the original receipt immutable.
3. For substantive problems such as excessive length, use at most one corrective
   model call per confirmed failed operation ONLY after an explicit paid-repair
   policy is approved. Reserve under the existing package-wide ceiling before
   dispatch. Never use an uncertain paid outcome as a retry trigger.
4. Revalidate evidence, completeness and every size/spend/tenant bound. A second
   failure stops with a precise explanation; it cannot loosen its own evaluator.
5. Checkpoint a successful correction and continue the same package. Completion
   means verified artifacts, not a reviewer vote or a successful worker return.
6. Source defects enter the existing durable workspace proposal/review path.
   Production filesystem edits are not repairs, and publication remains an
   owner decision.

No new scheduler, seats, permission grants or unbounded retries are required.
Diagnostics and stored outcomes should remain available when model access or
repair dispatch is unavailable. Existing repair controls remain authoritative;
this proposal does not enable them or grant a new spending permission.
